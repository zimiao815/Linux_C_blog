# read/write 与短读短写

- 核心问题：`read`/`write` 返回的字节数少于请求，是 bug 吗？正确写法是什么？
- 一句话结论：不是 bug。`read`/`write` 只承诺「最多」读写 N 字节，实际返回值可以比 N 小（短读/短写），也可能被信号打断返回 -1（`errno == EINTR`）。正确写法是把它们放进循环，累计已处理的字节数，直到「全部完成」「读到 0（EOF）」「遇到真正的错误」三者之一才停。
- 适用条件 / 范围：POSIX 通用语义；「短读短写是允许的」由 POSIX 保证；`read` 对普通磁盘文件「要么读满要么读 0」是 Linux 具体行为而非标准保证；EINTR 的语义在 Linux 与 POSIX 标准之间存在差异（标准允许自动重启，Linux 不自动重启）。示例在 Linux/macOS 上均可复现。
- 不处理：`write` 返回成功是否等于已落盘（第 5 篇 fsync）、非阻塞 I/O 与 `poll`/`select` 的完整配合（本片只讲阻塞模式下短读写与 EINTR）、`O_APPEND` 下的偏移行为（第 3 篇）、`pread`/`pwrite`（第 6 篇原子操作顺带）。
- 四类读者视角（各一句话）：
  - 搜索者：read 只读了一半、write 只写了一部分、或者被信号打断返回 EINTR，这行代码到底怎么写才对。
  - 学习者：read/write 是系统调用，返回值取决于内核此刻愿意/能够处理多少字节，短读短写是被允许的正常结果而非错误。
  - 编程者：把 read/write 包成「循环 + 累计」的完整读写函数，正确处理 EOF、EINTR、短读写和错误。
  - 求职者（按需）：read 返回 0 和返回 -1 各代表什么；EINTR 为什么要重试；为什么 read 会短读。
