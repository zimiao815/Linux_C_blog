# 02 研究记录：read/write 与短读短写

## 环境

- macOS 14.8.8（Darwin 23.6.0，x86_64）
- Apple clang 16.0.0
- 编译选项：`cc -std=c17 -Wall -Wextra -Wpedantic -Wconversion -Wshadow -O0 -g`

## 一手资料要点

### POSIX read(3p) / write(3p)

- read/write 的返回值语义：成功时返回实际读/写的字节数；这个数**可以小于请求的 nbyte**（短读/短写），这不是错误。
- read 返回 0 表示「到达文件尾」（EOF），对管道/终端表示「对端已关闭」。
- read 返回 -1 表示出错，errno 给出原因；其中 EINTR 表示「在读到任何数据之前被信号打断」。
- 慢系统调用（slow system call）被信号打断时返回 EINTR，这是 POSIX 允许的行为。

### Linux man-pages read(2) / write(2)

- Linux 对普通文件（regular file）的 read：**要么读满请求的字节数，要么返回 0（EOF）**；但对终端、管道、socket 等「流」型描述符，短读是常态。这是 Linux 的实现行为，不是 POSIX 标准保证。
- 管道（pipe）写超过 PIPE_BUF（POSIX 规定至少 512，Linux 上为 4096）时，write 不保证原子性，且可能发生短写。
- 非阻塞模式下，write 遇到「写不下」会返回 EAGAIN/EWOULDBLOCK；阻塞模式下则阻塞等待。

### EINTR 的关键差异

- POSIX 允许实现「自动重启」被信号打断的系统调用（SA_RESTART 行为）；Linux 默认**不**自动重启，read/write 被信号打断后返回 -1/EINTR，由调用者决定是否重试。
- 因此正确处理 EINTR 是 Linux 下写健壮代码的必要项；而在某些 BSD/macOS 上默认 SA_RESTART 会让部分慢调用自动重启（不同平台行为不同，不写死成定论）。

## 实验结论（均已实际编译运行）

| 实验 | 程序 | 现象 | 说明 |
|------|------|------|------|
| 短读 | short_read.c | 请求 read 4096 字节，返回 5 | 管道对端只写了 5 字节，read 立刻返回这 5 字节 |
| 短写 | short_write.c | 管道写满后 drain 100 字节，再写 65536 只写进 100 | 非阻塞写端，空间不够时只写能写下的部分 |
| EINTR | eintr.c | 阻塞 read 被 SIGUSR1 打断，返回 -1 且 errno==EINTR | 未设 SA_RESTART，慢调用被打断 |
| 完整读 | read_all.c | 循环累计，请求 10 字节读到 10 字节 | read_all 正确写法，处理 EINTR/EOF |

## 关键边界（写进正文）

1. 短读短写**不是错误**，是「内核此刻只愿意/只能处理这么多」的正常结果。
2. read 返回 0 是 EOF，不是「读失败」；read 返回 -1 才是失败，且要区分 EINTR（可重试）和其他 errno（真正错误）。
3. 普通磁盘文件的 read 在 Linux 上「要么读满要么 0」，但这是实现行为，可移植代码不该依赖它；对终端/管道/socket 短读随时可能发生。
4. 正确写法 = 循环 + 累计字节数 + 区分「读满/EOF/错误」三种终止条件。
5. write 对管道/SOCK_STREAM 也会短写，同样需要循环。
