# 标准 I/O 库第 5 篇：fflush 与刷新边界

- 核心问题：fflush 成功后，数据到哪一层了？
- 结论：对关联文件描述符的输出流，成功刷新把待输出字节交给底层文件；普通文件仍需单独请求持久化，管道仍需接收方处理确认。
- 范围：C 输出刷新语义、POSIX 文件流、glibc 2.40 与 Linux v6.6 普通文件路径。内存流仅标明例外。
- 实验：macOS 上比较 buffered、flush、sync-only、flush-sync；管道消费者不读取时刷新成功；文件大小限额触发刷新错误。
- 不展开：fclose 延迟报错、更新流切换、输入缓冲清理、事务原子替换。
- 搜索者：确认刷新成功到底承诺什么。
- 学习者：看清 FILE 缓冲、fd、内核页缓存的关系。
- 编程者：按可见性、持久化、业务确认选择接口，处理失败。
- 求职者：解释为什么先 fsync 再 fflush 顺序不对。

## 标题候选

- 搜索型：fflush 与 fsync 有什么区别？
- 通俗型：文件已经能读到了，为什么还不能算保存完成？
- 兼顾型（选用）：fflush 返回成功，数据就安全落盘了吗？
- 选择理由：问题直接，能由实际可见性实验和持久化接口规范共同回答。
