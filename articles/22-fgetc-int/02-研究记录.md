## 事实依据

| 关键判断 | 来源 | 范围 |
| --- | --- | --- |
| fgetc 成功返回 unsigned char 转换为 int 的值，结束和错误均可返回 EOF | POSIX.1-2024 fgetc；glibc 2.40 Character Input | 正文限定常见 8 位字节、int 能容纳全部字节值的环境 |
| EOF 是负的整型常量，不保证等于 -1 | POSIX stdio.h；本机 limits_probe.c | 本机和 glibc 为 -1，不硬编码 |
| 8 位字节的 256 种值加 EOF，需要区分 257 种结果 | 上述接口契约与本机整数范围 | char / unsigned char 都不能完整保存本篇全部结果 |
| 超范围有符号转换由实现定义或引发实现定义信号；无符号转换按范围折回 | SEI CERT INT31-C 引述 C 整数转换规则 | 使用 C17，255 转为 -1 仅为本机实测 |
| plain char 的符号性取决于实现，Clang 可用选项指定 | Clang 命令参考；三种编译模式实测 | 不依赖默认 signed char |
| glibc fgetc 对应 _IO_getc，缓冲快路径按 unsigned char 取值 | glibc 2.40 getc.c、struct_FILE.h、fileops.c | 用户态实现示意，不称为 macOS 内存现场 |
| ferror 检查流错误标志；fputc 输出失败返回 EOF | POSIX ferror、fputc；glibc EOF and Errors | POSIX 有效 ferror 调用不改变 errno；调用者及时诊断 |

## 实验复现

```sh
python3 linux_c_blog/articles/22-fgetc-int/verify.py
```

实际环境为 macOS 14.8.8 x86_64、Apple clang 16.0.0。未在 Linux 主机实测。

严格选项：`-std=c17 -Wall -Wextra -Wpedantic -Wconversion -Wshadow -O0 -g`。默认、`-fsigned-char`、`-funsigned-char` 三种模式均编译探针、范围程序和复制程序，无警告。

- 三次范围检查：CHAR_BIT=8、UCHAR_MAX=255、INT_MAX=2147483647、EOF=-1。默认和 signed 模式 CHAR_MIN=-128，unsigned 模式为 0。
- 九次输入观察：FF、ASCII A、空输入分别在三种模式下执行。signed 模式的 FF 与 EOF 均缩窄为 -1；unsigned 模式均缩窄为 255。观察器只读两次，不运行错误循环。
- 六次复制验证：三种模式分别复制全部 256 种字节和空输入，逐字节一致，退出 0。
- 四次失败验证：探针和复制程序分别读目录、向文件大小限额为 0 的输出写入。均退出 1，分别报告 Is a directory 和 File too large。

验证器在全新临时目录构建；每次运行有超时，临时目录自动清理。目录 fd 在 finally 中关闭；输出限制只在子进程设置。程序借用标准流，不额外打开资源，最终输出刷新纳入退出状态。

原始环境、退出码、输出保存在 verification.json / actual-output.txt。正文输出由 compose_article.py 从真实记录生成；两段 C 代码从源文件嵌入。copy_main.c 为独立测试入口，不塞入正文。

## 边界

显式 char 转换为观察信息损失而设，不是安全用法。转换发生在比较和整数提升之前，转回 int 无法恢复信息。EOF 并非文件中的特殊字节，也不是 UTF-8 解码机制。

copy_bytes 借用两个独立流；调用方负责关闭和资源生命周期。输入没有遗留错误，失败可能已产生部分输出，不回滚；fflush 不提供持久化保证。未测试信号中断、非阻塞流、并发和真实硬件故障。

正文机制没有展开内核调用，因此两张图专注 FILE、字节取值和类型转换，无无关内核对象。
