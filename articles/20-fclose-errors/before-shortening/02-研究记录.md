| 事实 | 一手依据 | 限制 |
| --- | --- | --- |
| fclose 处理未写缓冲并关闭关联文件，无论成功失败都解除流关联 | POSIX.1-2024 fclose DESCRIPTION，ISO C 对齐段落 | 不能从 EOF 推导流仍有效；不执行关闭后的非法访问 |
| 成功返回 0，失败 EOF，POSIX 设置 errno | POSIX fclose RETURN VALUE | 成功后不读旧 errno；不同实现返回的错误文本不必相同 |
| 缓冲接收成功与最终关闭写出成功不同 | POSIX fputs + fclose；实际 buffered 失败实验 | 小块完整进入缓冲是本机观察；不承诺所有 libc 都在相同调用时机失败 |
| 文件大小限制会触发 EFBIG 与 SIGXFSZ | POSIX getrlimit / setrlimit；实际子进程限额 | 只对子进程设置，忽略信号以观察错误返回；并非真实磁盘满 |
| 正常关闭路径先保存刷新结果，继续底层关闭和资源清理 | glibc 2.40 iofclose.c / fileops.c，_IO_new_file_close_it | 刷新失败并不让该路径直接返回并保留流；流状态和 fd 关闭状态分别讨论 |
| 库分配缓冲会释放，用户缓冲只解除关联 | POSIX fclose；glibc genops.c _IO_setb 的 _IO_USER_BUF 分支 | 局部 buffer 在 main 返回前仍有效，所有路径先 fclose |
| 内核 fd 表到文件对象关系、f_pos / f_inode / f_op 字段 | Linux v6.6 fdtable.h / fs.h | 源码对象示意，未在本机抓取 Linux 内存 |
| Linux close 先释放 fd，错误返回后盲目重关有编号复用风险 | Linux close(2) CAVEATS | 不将该裸 fd 行为写成所有 POSIX 平台保证；fclose 的旧流不可再用规则独立成立 |

## 实际结果

三种模式 × 三种限额，共 9 组：

- 无额外限额：三组均完整写入 9 字节并退出 0。
- 限额 0：buffered 的 fputs 成功，fclose 报 File too large，文件空；unbuffered 的 fputs 报错，fclose 成功；flush-first 的 fflush 和 fclose 均报错。三组均退出 1。
- 限额 4：三组保留 `reco` 前缀，报错时机与限额 0 对应模式一致，均退出 1。

另外验证：

- 缺参数、非法模式、目标已存在、父目录不存在，共 4 组拒绝，均退出 1。已存在文件保持 KEEP 原内容。
- close_fd_probe.c：普通成功、EFBIG 限额 0、EFBIG 限额 4，共 3 组。关闭前缓存整数 fd，关闭后只用 fcntl 检查该编号，全部为 EBADF；没有解引用或查询已关闭的 FILE。
- fd 探针是单线程，关闭到 fcntl 之间没有新 fd 分配。结果仅证明本机这些 EFBIG 路径已解除描述符关联，不推广到所有平台错误码。
- 正文 Python 启动器按原样执行，退出 1，输出为 fputs accepted / fclose File too large / exit=1，limited.txt 为 0 字节。

## 技术审查与修订

- 在技术审查中发现独立 fd 探针最初把 fileno 放在 setvbuf 前，已调整为首先 setvbuf；修改后从新临时目录重新构建运行，以上记录为最终版本。
- 主示例始终在其他流操作之前 setvbuf，自备局部缓冲活到关闭结束。
- payload fputs、fflush、fclose 的失败均保留整体失败状态；perror 在失败后立即调用，关闭错误另存 errno 后诊断。
- fclose 不重试，包括 EINTR；不拿 ferror、fileno 查询已关闭流。
- 关闭清理不会回滚前缀，代码未在错误路径自动删除结果或盲目重发。
- 未运行 double fclose / use-after-free 程序；失效规则由规范与源码支撑。
- fd 探针只作证据，正文只给主题所需的主程序与失败启动器。
