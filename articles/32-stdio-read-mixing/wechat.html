fread 读了一个字节，read 为什么接不上？

文件里是 abcdefghijklmnopqrstuvwxyz。程序先用 fread 取出 a，接着拿 fileno(fp) 得到的 fd 调用 read，希望它继续返回 b。

问题是，read 不知道 FILE 缓冲区里还放着什么。它从内核维护的文件偏移继续读取，而这个偏移可能已经被预读推进了一大截。没有交接就换入口，两个函数看见的位置可能对不上。

让同一个文件的读取从流切到 fd，必须连同缓冲状态和文件位置一起交接。复制一个 fd，也解决不了这个问题。

本篇沿用第 15 期的流位置、第 17 期的描述符归属，只讨论 POSIX 下的普通可定位文件。实验环境是 macOS 14.8.8、Apple clang 16.0.0，未在 Linux 主机实测。

这篇文章怎么读？先看预读留下的数据在哪里，再看一次合法的 fread → read → fread，最后把交接封装成短函数。

数据还在缓冲区，read 却绕过去了

第 15 期已经看到：流的位置和底层 fd 的偏移不一定相等。本期的问题是，程序中途换了一个读取入口。

假设库为了满足一次单字节 fread，从文件预读了全部 26 个字节。程序拿到 a 后，流的逻辑位置是 1，缓冲区里还有 b 到 z；内核中的文件偏移却已经到 26。

此时若绕过流直接读取，底层已经没有后续字节，因而能解释一些实现上“怎么突然读不到了”的现象。但未经协调的混用不符合 POSIX，结果未定义，不能保证每次都返回 0。这里的 26 只是机制示意，预读量也不是接口承诺。

这像书店柜台提前从仓库领了一摞书，只把第一本交给你。你转身去仓库要“下一本”，仓库已经从领走的那一摞之后继续找。没拿到的书仍在柜台，对应的就是尚未消费的流缓冲；仓库的取货进度，对应内核文件偏移。

真正的程序里，FILE * 和 fd 关联的是同一个打开文件描述，共享底层偏移，但只有标准 I/O 流管理那块用户态缓冲。read 不会到流缓冲区里找剩余字节。

切换入口之前，先交接位置

POSIX 把流和文件描述符都称为访问打开文件描述的“句柄”。当前正在使用的入口叫活动句柄；切换时，应用必须按规则协调。

本篇采用一条明确的路径：

交接方向 本例做法
流交给 fd 先成功调用 fflush(fp)，再 read
fd 交回流 取得 fd 当前偏移，再用 fseeko 显式定位流

第一步容易让人疑惑：fflush 不是刷新输出的吗？

POSIX 对可定位的输入文件也定义了 fflush 的行为。当流尚未处于 EOF 时，它把底层文件偏移校准到流的位置。这样，前面假设中的偏移就能从 26 回到 1，随后 read 才从 b 继续。

这不是通用的“清空输入”方法。ISO C 没有提供相同的输入流保证，终端和管道也不能照搬这套回退文件偏移的做法。

交回流时，本例用 lseek(fd, 0, SEEK_CUR) 取得新的偏移，再调用 fseeko(fp, pos, SEEK_SET)。这样既明确了流下一次从哪里读，也满足了本例涉及显式定位后的交接要求。

工程里把交接包起来

下面的 read_one_via_fd 让 fd 临时读一个字节，再把读取权交回流。它只用于独占访问的 POSIX 普通可定位文件，调用前流处于读取阶段；不涉及其他线程、进程同时改动偏移，也不支持待处理的 ungetc 数据。

函数返回 1 表示读到字节，0 表示 fd 读到文件结束，-1 表示失败。它借用 fp，不会关闭流或 fd。下面两段按顺序连接就是完整函数，头文件和声明见 read_one.c。

第一段完成交出流位置，并处理系统调用被信号中断的情况：

C
int read_one_via_fd(FILE *fp, unsigned char *out)
{
    int fd = fileno(fp);
    if (fd == -1 || fflush(fp) == EOF)
        return -1;                     // 先把流位置交给 fd

    ssize_t n;
    do {
        n = read(fd, out, 1);
    } while (n == -1 && errno == EINTR);
    if (n == -1)
        return -1;

第二段取得 fd 的新位置，再交回流：

C
    off_t pos = lseek(fd, 0, SEEK_CUR);  // 取得 read 后的偏移
    if (pos == (off_t)-1 || fseeko(fp, pos, SEEK_SET) != 0)
        return -1;                     // 再把位置交回流
    return (int)n;
}

若返回 -1，调用者应停止本轮读取并处理错误，不要假定位置没有变化：可能 read 已经取出了字节，后续定位才失败。无论成功失败，最终仍由持有流的调用者执行 fclose(fp)。

配套程序创建 26 字节临时文件，依次执行一次 fread、一次上述函数、再一次 fread。输出来自真实运行：

C
fread=a pos=1
read=b pos=2
fread_again=c pos=3

三次调用连续拿到 a、b、c。这里没有运行违规版本来凑一组“必然漏读”的输出；实验验证的是协调后的代码确实接得上。

附带测试还逐字节比较了 10000 字节文件，覆盖所有 256 种字节值，并检查空文件、单字节文件和 EOF。错误路径用测试替身注入 EINTR 与 EIO，分别验证重试和失败返回。

哪些办法不能替代交接

dup(fd) 得到的是另一个描述符号码，仍指向同一个打开文件描述，共享偏移。fdopen 也不会自动复制 fd。两种操作都不能让读取位置彼此独立。

clearerr(fp) 只清除 EOF 和错误指示器，既不把未读字节交给 read，也不修正底层偏移。

第 16 期讲的是同一个更新流内部的读写切换；本期则是流和 fd 之间切换活动句柄。不要因为这里用了输入流上的 fflush，就把它当成标准 C 更新流“读后写”的通用替代操作。

如果业务没有必须调用 read 的理由，整段逻辑都使用 fread 最省事。只有接口边界确实要求两套方式交替使用时，再把交接写成明确步骤，并检查每一步的返回值。
