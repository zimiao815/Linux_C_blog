r+ 文件为什么不能直接读完再写？

用 r+、w+ 或 tmpfile 打开的流既能读又能写，很多人会自然地把它当成“读写权限都打开了，所以随时可以切换”。真正容易出错的地方在切换本身：读写操作不能任意紧挨着发生。

C 标准对更新流规定了明确的过渡条件：输出后接输入，必须插入 fflush 或文件定位操作；输入后接输出，必须插入文件定位操作，除非输入操作已经遇到 EOF。这里的定位操作包括 fseek、fsetpos 和 rewind。

先记住一句话：更新流不是两条互不相关的通道。写完想读，先刷新或定位；读完想写，先定位。不要用一次“看起来能跑”的结果替代这个规则。

这篇文章的实验运行在 macOS 14.8.8、Apple clang 16.0.0，未在 Linux 主机实测。示例使用 tmpfile 创建普通临时更新流，只运行符合标准切换规则的顺序。

这篇文章怎么读？先看一个合法的写后读、读后写流程，再把两个方向需要的过渡操作分开记住。

+ 代表更新，不代表可以随便切换

模式中的 + 把流打开为 update stream，也就是同一个 FILE * 可以执行输入和输出。它解决的是“允许读写”这件事，没有取消缓冲区和文件位置的规则。

把更新流想成一个既能进货又能出货的仓库。写操作把货物先放进仓库的待发区，读操作却要从另一套进货记录继续取货。仓库需要先完成交接手续，才能知道下一步应该面对哪一批数据。fflush 像把待发货物交给运输部门，fseek 像重新确认库存位置。

这个类比只用来说明“切换需要交接”。真实程序中，fflush 处理输出缓冲；fseek、fsetpos、rewind 改变或确认流的位置，并处理相应的流状态。它们不是万能的同步锁，也不能替代并发控制。

两个方向的规则不一样

输出接输入时，至少要有一次 fflush 或定位操作：

C
fwrite(data, 1, count, fp);
fflush(fp);
fseek(fp, 0, SEEK_SET);
fread(data, 1, count, fp);

输入接输出时，必须有一次定位操作：

C
fread(data, 1, count, fp);
fseek(fp, 0, SEEK_END);
fwrite(extra, 1, extra_count, fp);

第二个方向不能只调用 fflush。fflush 的主要作用是处理输出缓冲，不能单独完成“从读切到写”的定位要求。输入操作如果已经读到 EOF，则标准允许随后直接输出，但把代码写成显式定位通常更容易读，也更不容易因为输入来源变化而出错。

一次实验验证合法切换

下面的程序先写入 abc，刷新并定位到开头后读取 a；然后再次定位到文件末尾，写入 X，最后定位到开头读回完整内容。

C
#include <stdio.h>

int main(void)
{
    char buf[5] = {0};
    FILE *fp = tmpfile();
    if (fp == NULL)
        return 1;

    if (fwrite("abc", 1, 3, fp) != 3 || fflush(fp) != 0 ||
        fseek(fp, 0, SEEK_SET) != 0)
        return 1;
    int first = fgetc(fp);

    if (fseek(fp, 0, SEEK_END) != 0 || fwrite("X", 1, 1, fp) != 1 ||
        fflush(fp) != 0 || fseek(fp, 0, SEEK_SET) != 0)
        return 1;
    if (fread(buf, 1, sizeof buf - 1, fp) != sizeof buf - 1)
        return 1;

    if (printf("write_then_read=%c\nread_then_write=%s\n", first, buf) < 0)
        return 1;
    return fclose(fp) == EOF;
}

输出如下：

C
write_then_read=a
read_then_write=abcX

第一段中，fwrite 后的 fflush 和 fseek 让读取从文件开头开始。第二段中，读完 a 后用 fseek(..., SEEK_END) 明确把下一次写入放到文件末尾，写入 X 后再次刷新并定位，最后才能稳定读回 abcX。

实验没有运行“写后直接读”或“读后直接写”的违规版本，因为那类代码不应靠一次机器输出判断对错。即使某个平台上看起来能工作，也不能把它当成可移植的标准 C 行为。

工程代码怎样选择操作

如果一段代码只读文件，就用只读模式；只写文件，就用只写模式。只有确实需要在同一个流上交替读写时，才使用 r+、w+ 或 a+，并把切换操作写在相邻位置，让规则一眼可见。

普通文件中，推荐使用 fseek、fsetpos 或 rewind 管理流的位置。不要一边用 fread，一边直接用同一个对象的 read；上一期已经看到，标准 I/O 可能提前读入缓冲区，系统调用看到的偏移可能不是程序以为的位置。若必须混用，还要遵守 POSIX 的活动句柄协调规则。

fflush 和 fclose 的返回值也不能忽略。刷新或关闭失败时，前面看似成功的输出仍可能没有完成。更新流的切换规则和错误检查要一起写，才不会把一个偶然可运行的顺序带进工程代码。
