# 研究记录：硬链接与 inode

## 核心事实与依据

| 技术判断 | 直接资料 | 核验结果 |
| --- | --- | --- |
| `link` 新增同一文件的目录项，st_dev/st_ino 保持相同 | POSIX link、stat；Linux link(2) | 实验两个名字 dev、ino 相同 |
| 新建硬链接使 nlink 加一，unlink 一个名字使其减一 | POSIX unlink、Linux inode(7) | 输出 2 → 1，第二名字仍可访问 |
| 删除最后名字后，fd 或 mmap 引用仍会延后内容释放 | POSIX unlink、Linux unlink(2) | 正文解释，示例实测一个 fd 场景 |
| 硬链接通常要求同一文件系统 | POSIX link、Linux link(2) | 正文写典型 EXDEV，未伪造跨挂载实验 |
| 目标已存在返回 EEXIST，普通目录硬链接通常 EPERM | Linux link(2)；本机受控程序 | link_errors.c 输出通过 |
| 比较对象身份要同时看 st_dev 和 st_ino | POSIX stat；Linux inode(7) | 正文明确单 inode 不足 |
| linkat 可使用目录 fd 作为相对路径起点 | POSIX link、Linux link(2) | 工程章节区分起点固定与对象锁定 |
| Linux VFS 和 ext4 分别处理路径、目录项和 nlink | Linux v6.6 namei.c、fs.h、ext4/namei.c | 机制叙述限定实现版本 |

## 实测记录

2026-10-06 在 macOS 14.8.0 / Darwin 23.6.0 x86_64 使用 Apple clang 16.0.0，严格参数 `-std=c17 -Wall -Wextra -Wpedantic -Wconversion -Wshadow -O0 -g` 编译两个程序，无警告。

- 创建硬链接后：两个名字 dev=16777222、ino 相同，nlink=2，size=22。
- 删除 original.txt 后：second-name.txt 仍为同一 dev/ino，nlink=1，内容仍为 `same inode, two names`。
- 目标名字已经存在：`File exists`，对应 EEXIST。
- 源对象是目录：`Operation not permitted`，对应 EPERM。

设备号、inode 数字和错误文本属于本机输出；稳定事实是身份字段相同、链接计数变化和内容仍可读。完整输出、命令、编译器和限制见 verification.json 与 actual-output.txt。

## 实现边界

示例用 `mkdtemp` 建立临时目录，明确处理路径构造、write 的 EINTR/短写、read 的 EINTR、close 和清理错误。没有实测跨文件系统 EXDEV、并发替换、网络文件系统或最后一个 fd 关闭后的空间回收时机。

对象图中的 files_struct、fdtable、struct file、inode 是 Linux 6.6 源码核对后的关键关系；macOS 实验只证明 POSIX 接口的可观察结果，不证明 macOS 内核使用相同内部结构。
